## 클라우드 저장 · 계정 — 회원가입/로그인 (0.7.0)

기록을 계정에 저장하고 다른 기기에서도 이어 볼 수 있다. **받는 정보는 이메일과 비밀번호 둘뿐**이고
이름·닉네임·전화번호는 어디에서도 묻지 않는다(요청 본문도 `{email, password}` 뿐임을 테스트로 확인).
로그인하지 않으면 예전과 똑같이 `localStorage` + `IndexedDB` 로만 동작한다.

- **헤더의 구름 배지**: 로그인하면 초록 점, 누르면 계정 화면(로그인 전) / 설정의 클라우드 카드(로그인 후).
- **설정 › 클라우드 · 계정**: 로그인한 이메일 · 동기화 상태(방금 동기화됨 / 동기화 대기 중 /
  클라우드 설정 대기 중 / 다른 기기 기록과 다름 / 동기화 실패 / 오프라인 · 로컬 저장) ·
  `[지금 동기화] [로그아웃] [이 기기 기록 올리기] [클라우드에서 불러오기] [비밀번호 재설정 메일]`.
- **아이디·비밀번호를 모두 이메일로 찾는다**
  - 비밀번호 찾기 → `POST /auth/v1/recover?redirect_to=…` → 메일 링크로 돌아오면
    `#access_token…&type=recovery` 를 읽어 **새 비밀번호 화면이 자동으로 열린다** → `PUT /auth/v1/user`.
  - 이메일로 로그인(매직링크) → `POST /auth/v1/otp` `{email, create_user:true}` → 링크를 누르면 비밀번호 없이 로그인.
    가입 여부가 헷갈릴 때도 이 메일로 확인된다. 확인 메일 다시 받기도 `POST /auth/v1/resend`.
  - 회원가입은 확인 메일을 거친다(프로젝트의 `mailer_autoconfirm=false`). 메일 링크를 누르면
    `#access_token…&type=signup` 으로 돌아와 바로 로그인된다.
- **저장 구조**: `sake_note_journals` 한 행(`user_id` PK · `data` jsonb · `updated_at`)에 업장·방문·주류 JSON.
  사진은 `sake-note-photos` 버킷의 `{user_id}/{photo_id}.jpg` 에 올리고 기록에는 `idb:{photo_id}` 참조만 남긴다
  (base64 를 DB 에 넣지 않는다). 다른 기기에서 열면 그 사진을 내려받아 IndexedDB 에 캐시해 오프라인에서도 보인다.
- **보내지 않는 것**: AI·카카오 API 키(`apiKey`·`apiKeys`·`kakaoKey`)는 클라우드 payload 에서 빼고,
  클라우드 기록을 불러올 때도 이 기기에 있던 키를 그대로 둔다. 사진 바이너리도 JSON 에는 넣지 않는다.
- **강제 덮어쓰기 없음**: 로그인 직후나 시작할 때 클라우드와 이 기기 기록이 **둘 다** 있으면
  `어느 기록을 쓸까요?` 로 물어보고 `[클라우드 기록 불러오기] [이 기기 기록 올리기] [나중에]` 중에 고른다.
  같은 이유로 이 기기가 아직 안 올린 변경이 있는데 다른 기기에서 기록이 바뀌었으면(충돌) 아무것도 덮어쓰지 않고
  `다른 기기 기록과 다름` 으로 멈춰 둔다.
- **SQL 전이면**: 테이블·버킷이 없어도 앱은 깨지지 않고 `클라우드 설정 대기 중` 으로 남아 로컬 저장을 계속한다
  (PGRST205 · 404 · `Bucket not found` 를 구분해 안내).
- **RLS**: 모든 테이블·Storage 접근은 `auth.uid() = user_id` / `(storage.foldername(name))[1] = auth.uid()::text`.
  앱에는 publishable 키만 있고 secret·service_role 키는 쓰지 않는다.

### Supabase 대시보드에서 할 일 (1회)

1. **SQL Editor** → `supabase-setup.sql` 전체를 붙여 넣고 Run
   (테이블 `sake_note_journals`, RLS 4개 정책, `updated_at` 트리거, 비공개 버킷 `sake-note-photos` + Storage 정책 4개).
2. **Authentication → URL Configuration**
   - `Site URL`: `https://sakenoteproject.vercel.app/`
   - `Redirect URLs`: `https://sakenoteproject.vercel.app/**`
     (예비 주소 `https://circlekim87-ctrl.github.io/sake-sushi-log/**` 도 함께 넣어 두면 두 주소에서 모두 링크가 돌아온다)
   이 설정이 없으면 확인·재설정·매직링크 메일이 `localhost` 로 돌아가 링크가 동작하지 않는다.
3. (선택) **Authentication → Emails**: 기본 메일 발송은 시간당 횟수 제한이 있어, 여러 번 시험하면
   `메일을 너무 자주 보냈어요` 안내가 뜰 수 있다.

## 위치 기반 업장 추론 (`nearby.js`)

사진 EXIF의 GPS로 업장을 찾는다.

1. **이미 가 본 업장**: 설정한 조회 반경(기본 5m) 안에 있으면 자동 선택 (기존 기능).
2. **처음 가는 업장**: 같은 반경의 업장 후보를 `+ 기록` 화면에 칩으로 보여 주고, 누르면 업장명·지역·주소가 채워진다.
   - **기본 반경 5m** — 사진을 찍은 바로 그 자리(그 업장)만 후보가 되도록 좁혀 두었다.
   - 실내 GPS 오차(10~30m)로 0건이면 `반경 5m 내에 등록된 업장이 없어요.` 안내와 함께
     원클릭 **`[30m로 넓혀 찾기]`** 버튼을 보여 준다(30 → 100 → 200m 단계).
   - 설정 › **위치 · 업장 추론 › 기본 조회 반경**(`5m` 기본 / `20m` / `50m` / `100m`)에서 직접 바꿀 수 있고,
     바꾸면 열려 있는 기록의 조회가 그 반경으로 즉시 다시 돈다.
   - 설정에 **카카오 로컬 REST API 키**가 있으면 카카오 로컬(음식점 `FD6`, 거리순) 우선.
   - 키가 없거나 카카오가 실패하면 OpenStreetMap — Overpass API(음식점·바·퍼브·이자카야 등)와
     Nominatim 역지오코딩(`accept-language=ko`)으로 동네명·주소를 얻는다.
   - Overpass·카카오의 조회 반경 파라미터와 클라이언트 거리 필터가 모두 같은 설정 반경을 쓴다(허용 오차 없음).
   - 로딩 표시, 실패·타임아웃 시 안내 문구와 `다시 찾기`, 수동 입력은 항상 열려 있다.
   - **로딩은 어떤 경우에도 끝난다** — 개별 요청 4초(`AbortController` + `setTimeout`,
     `AbortSignal.timeout()` 같은 최신 API 미사용), 한 번의 조회 전체 6.5초, 안전망 8초(watchdog).
     Overpass가 무응답·30초 지연이어도 8초 안에 실패 폴백(`주변 업장을 조회하지 못했어요` + `다시 찾기`)으로 넘어간다.
   - Overpass가 실패하면 기다리지 않고 곧바로 보조 미러 + Nominatim 검색을 **동시에** 시도하고,
     Nominatim은 공공 API 정책(초당 1회)을 지키는 게이트를 거친다. 지역명(역지오코딩)은 남은 예산만 기다린다.
   - **결과 없는 좌표를 '찾는 중'으로 계속 그리지 않는다.** 조회가 예약되지 않은 상태면
     `주변 업장을 아직 찾지 않았어요 [주변 업장 찾기]` 안내를 보여 주고, 이미 내 업장과 매칭된 기록에서는
     추천 영역을 **접은 채** `[이 위치 주변 업장 다시 찾기]` 버튼만 남긴다(누르면 다시 열리고 `[접기]`로 닫는다).
   - **사진을 더하거나 빼서 GPS 중앙값이 바뀌면 앞서 잡은 업장을 다시 판단한다.** 잡혀 있던 업장의 좌표가
     새 중앙값에서 `max(설정 반경, 50m)` 보다 멀면 `venueId` 연결을 풀고, 자동으로 채운 값이면
     이름·지역·주소·업장 좌표까지 비운다(직접 입력·선택한 이름은 남긴다). 새 위치의 후보를 바로 다시 찾는다.
     사진을 모두 지우면 사진에서 나온 위치·자동 업장도 함께 비운다.
   - **사진을 모두 지우면** 사진에서 나온 위치·자동 업장도 함께 비운다.
   - '샘플로 체험'한 기록에 내 사진을 고르면 샘플 사진·사케 초안을 먼저 비우고 새 사진 좌표로 판단한다
     (샘플 좌표가 남아 GPS 중앙값이 샘플 업장에 머무는 일을 막는다).
   - 역지오코딩한 동네명은 `② 촬영 정보` 의 위치 줄에도 붙는다(`위치 37.52000, 127.05000 · 서울 강남구 역삼동`).
     좌표별 캐시를 두어 후보 상자와 같은 값을 쓰고, 결과가 도착하면 그 자리에서 채운다.
   - 반경 안에 아무것도 없다는 응답(0건)과 통신 실패·오프라인을 구분해 0건일 때만 `[30m로 넓혀 찾기]`를 띄운다.
   - 한 위치·반경의 조회 결과는 메모리에 캐시한다(같은 좌표 재조회 없음). 늦게 도착한 응답은
     조회 세대(`_nearbySeq`) 로 무시해 새 상태를 덮지 않는다.
3. 외부로 나가는 값은 **좌표뿐**이다(사진·기록·개인정보 전송 없음). 지도 데이터 © OpenStreetMap contributors.

이 때문에 빌드는 이제 지도 API 세 곳에만 선택적으로 접속한다. 나머지 기능은 여전히 오프라인 단일 파일이다.

## 언어 전환 — 한국어 · English · 日本語 (0.3.0)

- 설정 맨 위에 **`한국어 / English / 日本語`** 세그먼트 버튼을 두고, 헤더 오른쪽 **`KO`·`EN`·`JP` 배지**를 누르면
  설정이 바로 열린다(언어 항목이 가장 위). 선택은 `localStorage[sakeSushiLang]` 에 저장되어 새로고침·재방문에도 유지된다.
- 화면의 한국어 문구를 사전(`i18n.json`)으로 바꾼다. 사전 키는 **원본 한국어 문구 그대로**이고,
  `{n}` 은 숫자, `{a}`·`{b}` 는 임의의 글자를 받는다(예: `마신 사케 {n}병` → `{n} bottles tasted` / `飲んだ酒 {n}本`).
- 적용 대상은 text node 와 `placeholder`·`aria-label`·`title`·`alt` 뿐이다. `input.value`·저장 데이터·사진은 건드리지 않으므로
  업장명·사케명·시음 메모 같은 **내 기록은 원문 그대로** 남고, 등급·화입 값은 한국어 키로 저장된 채 화면 이름만 번역된다.
- 한국어 원문은 노드에 기억해 두었다가 한국어로 돌아오면 그대로 복원한다(`node.__i18nSrc`).
  새로 그려지는 화면은 `MutationObserver` 가 20ms 디바운스로 따라가 번역한다.
- 날짜·월 표기는 코드에서 언어를 따른다 — `11월 14일 (토)` / `Nov 14 (Sat)` / `11月14日 (土)`,
  `2026년 11월` / `November 2026` / `2026年11月`.
- 역지오코딩·업장 검색의 Nominatim 은 **선택 언어로 `accept-language`** 를 보내고, AI 라벨 인식은
  **시음 메모를 선택 언어로 쓰도록** 프롬프트에 한 줄을 더한다(브랜드·등급 값은 그대로).
- 번역하지 않는 것: 예시 데이터(업장·사케 이름·메모·지역), 언어 이름 자체(`한국어`/`English`/`日本語`), 숫자·좌표.

## 사진 20~40장을 한 번에 (0.4.0)

- **아이폰 사파리에서 20장을 골라도 1장만 등록되던 원인**: `change` 이벤트에서 고른 목록(`input.files`, FileList)을
  읽는 도중 `input.value = ''` 로 입력칸을 비우면 **FileList 도 함께 비워진다**. 한 장씩 비동기로 읽는 사이
  목록이 비어 두 번째 장부터 사라졌다. 이제 목록을 먼저 배열로 복사한 뒤(`filesOf()`) 입력칸을 비운다.
  같은 사진을 다시 고를 수 있도록 입력칸은 계속 비운다.
- **저장 용량**: 사진 바이너리는 **IndexedDB**(`sakeNotePhotos` › `photos`)에 넣고, 기록(`localStorage`)에는
  `idb:<id>` 참조 문자열만 남긴다. iOS 사파리의 localStorage 5MB 한도에 걸리지 않아 40장도 한 번에 저장된다.
  - IndexedDB 를 못 쓰는 브라우저(사생활 보호 모드 등)에서는 예전처럼 data URL 을 기록에 넣는다(그때는 장수를 줄여야 한다).
  - 예전 기록에 data URL 로 들어 있던 사진은 처음 열 때 한 번 IDB 로 옮긴다(`photoMigrateInline`).
  - 지운 기록·사진은 저장소에서도 지우고(`photoDel`·`photoGc`), 설정 › 데이터에 `사진 N장(용량)` 이 표시된다.
  - JSON 내보내기에 사진도 함께 담고(`photos`), 가져오면 IDB 로 복원한다.
- 등록 중에는 `사진 3/36장 불러오는 중…` 처럼 진행 상황을 보여 주고, 끝나면 `사진 36장 추가 · EXIF 없는 2장은 파일 시각 사용` 처럼 결과를 알린다.
- 사진 단계 머리글에 `사진 36장` 장수를 표시하고, 방문 상세의 사진도 `사진 40장` 으로 센다.

## Gemini 503(서버 과부하) 폴백 (0.4.1)

실기기에서 무료 Gemini 키로 라벨을 읽을 때 구글 쪽이 `503 · This model is currently experiencing high demand.`
를 돌려주면 앱이 **바로 실패 처리**해서 다음 모델로 넘어가지 못했다. 그래서 폴백 조건과 안내 문구를 고쳤다.

- 폴백 조건: `404`(모델 없음) · `400`(요청 거부) · `429`(한도) 에 **`500`·`502`·`503`·`504`(서버 과부하·오류)** 를 더했다
  (`aiRetryable()`). 키 오류(401·403)는 모델을 바꿔도 같으므로 예전처럼 바로 안내로 끝난다.
- 호출 순서(모두 무료 티어): `gemini-3.8-flash` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite`
  → `gemini-3.6-flash` → `gemini-4-hydrogen`. 큰 모델이 503 이어도 lite 모델이, 3 계열이 통째로 막혀도
  4 세대 무료 모델이 응답할 수 있게 사슬을 넓혔다. `gemini-2.5-flash`(기존 사용자 전용·12-01 라우팅)와
  `gemini-2.0-flash`(목록에서 사라짐)는 넣지 않았다.
- 모두 429·5xx 면 `구글 AI 서버가 일시적으로 혼잡해요. 잠시 후 다시 눌러 보세요.` 로 끝난다.
- 키가 이미 연동된 상태의 실패 안내에서 `· 데모 채우기로 체험할 수 있어요.` 를 뺐다(데모 상태로 오해했다).
  이제는 `AI 인식 실패: … · 잠시 후 다시 시도해 주세요.` 또는 위 혼잡 안내만 나온다.
  사진이 안전 필터에 걸린 경우는 원인만 알리고, 모든 모델이 빈 답을 주면
  `라벨을 읽지 못했어요. 글자가 잘 보이는 사진으로 다시 시도해 주세요.`,
  연결 자체가 안 되면 `AI 서버에 연결하지 못했어요. 인터넷 연결을 확인하고 잠시 후 다시 시도해 주세요.` 로 안내한다.
- 검증: `verify_gemini.py` 가 503·500 폴백(첫 모델만 실패 → 둘째 모델 응답으로 채움), 전 모델 503(사슬 5개 전부 시도 ·
  혼잡 안내 · 입력칸 유지 · '데모' 문구 없음), 401 즉시 안내, 빈 답·연결 실패 안내를 모의 응답으로 확인한다.
- 이 컨테이너에서는 Gemini 엔드포인트가 403 으로 막혀 있어 실제 503 을 재현할 수 없다.
  모델 ID·무료 티어는 2026-11-20 공식 모델 목록·가격표(Free of charge 표기)로 확인했다.

## N번째 방문 · 브랜드별 사케 히스토리 (0.5.0)

### 같은 업장 N번째 방문 카운팅
· 방문을 **업장별로 날짜+시간 오름차순**으로 세어 `1번째 방문`, `2번째 방문` … 배지를 붙인다.
  업장은 `venueId` 기준이고, **이름이 같은 업장 기록은 하나로 묶는다**(띄어쓰기·대소문자 무시).
· 업장별 화면 맨 위에 **업장 요약**을 두었다 — 업장마다 `총 N회 방문` 과 `최근 방문 날짜`,
  0.6.0 부터는 누르면 그 업장의 **날짜별 기록**(아래)이 열린다. 목록만 거르려면 업장 칩을 쓴다.
· 방문 카드의 업장명 옆, 그리고 **방문 상세 시트**(주소 줄 아래)에 `N번째 방문` + `총 N회 방문` 이 보인다.
  사케 상세의 '마신 곳' 옆에도 그 방문이 몇 번째인지 붙는다.
· 순번은 저장하지 않고 **그릴 때마다 다시 계산**한다(방문 목록·업장명·날짜가 바뀌면 캐시 서명이 달라져 재계산).
  그래서 방문을 추가·삭제하거나 날짜를 바꿔도 순번이 저절로 맞는다. 업장이 없는 방문에는 배지가 없다.

### 브랜드별 사케 히스토리 (사케 목록 탭)
· 사케 목록 위에 **`브랜드별` ↔ `최신순 전체`** 세그먼트를 두었고, 기본은 `브랜드별` 이다.
· 브랜드 추출 순서: ① 이름과 양조장의 공통 앞부분(`바라 마송 레 마르간` ↔ `바라 마송 · 샹파뉴` → `바라 마송`)
  → ② 이름 앞머리의 첫 낱말(등급·숫자·`슈조/주조` 같은 고리말은 건너뜀; `덴슈 욘와리코부…` → `덴슈`)
  → ③ 양조장 앞머리. 띄어쓰기·대소문자·문장부호·`텐주/덴슈` 같은 표기 차이는 하나로 묶는다.
· 섹션 헤더: **브랜드명 · 총 N병(N회) · 최근 마신 날**. '회'는 그 브랜드를 마신 방문 수다.
· 섹션 안에는 마신 날짜 최신순으로 **사케 풀네임 · 등급/정미보합 · 마신 업장(+몇 번째 방문) · 날짜 · 사진/메모**가
  한 줄씩 쌓이고, 누르면 사케 상세가 열린다. 사진은 라벨 사진이 있으면 썸네일로 보여 준다.
· 헤더를 누르면 **접기/펼치기**(`aria-expanded`), 검색어·등급 칩은 두 보기 모두에 그대로 적용된다.
· 새 문구(`{n}번째 방문` · `총 {n}회 방문` · `총 {a}병({b}회)` · `최근 마신 날 {a}` · `브랜드별` · `최신순 전체`)는
  `i18n.json` 에 영어·일본어까지 넣어 `i18n_coverage.py` 미번역 0개를 유지한다(브랜드 이름 자체는 데이터라 원문 유지).
· 데모 데이터에 같은 업장의 지난 방문(`t0`, 2026-10-18)을 하나 더 넣어 `2번째 방문` 과 `고쿠류 3병(3회)` 이
  실제 화면에서 보이게 했다.
## 주종 분류 · 업장 날짜별 기록 (0.6.0)

### 주종 4개 — 사케 · 와인 · 전통주 · 위스키
· 주류 레코드에 `category`(`sake`|`wine`|`traditional`|`whisky`)를 둔다. 값이 없는 예전 기록은 **사케**로 본다
  (`normalizeState` 가 채우므로 JSON 가져오기·씨드 모두 같은 규칙).
· 주류 목록 맨 위에 **주종 요약 카드 4개**(`사케 10병` `와인 2병` `전통주 1병` `위스키 1병`)를 두고,
  카드를 누르면 그 주종만 보이고 다시 누르면 전체로 돌아온다. 등급·종류 칩도 고른 주종 안의 값만 보여 준다.
· 보기는 **`분류별`(기본) · `브랜드별` · `최신순 전체`** 세 가지다.
  `분류별` 은 주종 섹션(`사케 · 총 N병(N회) · 최근 마신 날`) 안에 브랜드 섹션을 다시 넣은 2단 구조이고,
  주종 섹션·브랜드 섹션 모두 접기/펼치기(`aria-expanded`)가 된다.
· 브랜드 묶음은 **주종 + 브랜드** 기준이다(같은 이름이라도 사케와 와인은 다른 묶음).
  와인·전통주·위스키는 이름이 큐베·제품명이라 **생산자(도멘·양조장·증류소)** 를 브랜드로 삼는다 —
  `도멘 루이 자도` → `루이 자도`, `전주 이강주` → `이강주`, `발베니` → `발베니`.
  생산자 앞뒤의 `도멘·샤또·증류소·샹파뉴·보르도` 같은 말은 브랜드에서 뺀다.
· 주종 배지는 목록 카드·브랜드 섹션 헤더·방문 상세·업장 기록에 모두 붙고, 색으로 구분된다(사케 회갈색 · 와인 자주 · 전통주 녹색 · 위스키 호박색).
· 입력 폼의 **주종 칩**을 고르면 라벨과 항목이 바뀐다 —
  사케(등급·정미보합·주조미·화입) / 와인(종류·빈티지·품종) / 전통주(종류·원료) / 위스키(종류·숙성연수·캐스크).
  주종을 바꾸면 앞서 고른 등급·종류는 지운다(서로 맞지 않는 값이 남지 않게).
· AI 라벨 인식 프롬프트는 `category` 를 함께 답하게 하고, 사진이 와인·위스키여도 주종·생산자·빈티지·숙성연수를
  채운다. 위스키는 도수, 와인은 품종까지 받는다.

### 업장 상세 — 날짜별 기록
· 업장별 화면의 업장 줄을 누르면 그 업장의 방문이 **최신순 날짜 타임라인**으로 열린다.
· 방문마다 날짜·시간·`N번째 방문` 이 머리에 붙고, 그 아래에
  **그날 먹은 음식**(사진 썸네일 5장 + `+N` · 방문 메모)과 **마신 주류**(주종 배지 · 이름 · 생산자/스타일 · 별점)가
  한 카드에 함께 정리된다.
· 날짜 줄을 누르면 방문 상세, 주류 줄을 누르면 주류 상세, 사진을 누르면 크게 보기가 열린다.
· 같은 이름의 업장은 하나로 묶어 세므로 업장 요약의 `총 N회 방문` 과 타임라인 길이가 같다.
· 새 문구(`날짜별 기록 · 최신순` · `그날 먹은 음식` · `마신 주류 {n}병` · `사진 {n}장 · 눌러서 크게 보기`
  · `이 업장만 모아 보기` 등)는 `i18n.json` 에 영어·일본어까지 넣어 `i18n_coverage.py` 미번역 0개를 유지한다.

## 이 작업 환경에서의 재검증

`verify_ui.py` 는 Chromium(Playwright)으로 실제 화면을 캡처하고 콘솔 오류·이미지 로딩을 확인한다.
`verify_nearby.py` 는 EXIF GPS 사진(`fixtures/exif_3712.jpg` · `exif_3755.jpg` · `exif_3756.jpg` · `exif_5292.jpg`)을 실제로 업로드하고,
Overpass·Nominatim 응답을 가로채 **기본 5m 후보 → 0건 안내 → 30m 넓혀 찾기 → 설정 반경 100m 반영**,
자동 채움 → 저장, 실패 폴백, 검색 폴백까지 검증한다.
이어서 **새 사진으로 위치가 바뀔 때의 재판단**을 같은 파일에서 검사한다 — 샘플 체험 → 사진을 한 장씩 삭제(위치·자동 업장 비움)
→ 새 좌표 사진 1장(업장 해제·추천 상자 열림·새 좌표로 후보 조회) → ② 위치 옆 동네명 → 후보 선택,
그리고 접힌 `[이 위치 주변 업장 다시 찾기]` → `[접기]` 토글. 아이폰 SE 폭(320px)·일반(375px)에서
날짜·시간 입력칸이 카드 안에 들어오고 가로 스크롤이 없는지도 확인한다(수정 전 빌드에서는 320px 에서
시간 칸 오른쪽이 카드 밖으로 29px 나갔다). 스크린샷은 `screenshots/13`~`26`.
이어서 **타임아웃·느린 응답 회귀 시나리오**를 같은 파일에서 검사한다(저장소가 빈 새 컨텍스트에서 돈다).

- Overpass 무응답 / 30초 지연 → 로딩이 **8초 안에** 끝나고 실패 폴백 표시
- 로딩 중에도 업장명·지역·주소 입력과 저장이 된다
- 후보를 고른 뒤 사진을 더 넣어 좌표가 바뀌어도 '찾는 중'이 남지 않는다
- 업장명을 먼저 입력한 뒤 사진을 넣어도(자동 조회 예약) 로딩이 끝난다
- 오프라인(`navigator.onLine=false`)이면 바로 안내
